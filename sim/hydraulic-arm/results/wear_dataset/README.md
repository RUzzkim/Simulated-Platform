# 关节轻度磨损仿真数据集

由 `python_twin/wear_dataset.py` 生成。模拟减速器/关节轴承的**缓慢轻度磨损**
（不停机），批量产出带磨损标签的关节时序，供边端故障检测、云端分析、ML 训练用。

> 边界：这是**仿真数据，不是真机实测**。磨损特征物理上成立，但幅值未对标真机，
> 不能当现场绝对阈值。仅用于算法/模型开发与方法验证。

## 怎么生成的

```
cd sim/hydraulic-arm/python_twin
python wear_dataset.py                      # 默认批次
python wear_dataset.py --joints 2,5 --seeds 4 --period 4 --t-end 8
python wear_dataset.py --smoke              # 单条基线 + 稳定性自检
```

- **轨迹**：home↔target 的连续正弦往复（`--period` 控制周期）。用连续运动是为了
  避开主 `../README.md` §4.5 记录的**保持段执行器失稳**——那与磨损无关，会污染标签。
- **控制器**：PID 基线，用**名义参数**构造（不知道磨损），符合真实工况。
- 每条样本对某一关节施加磨损，其余关节健康；另有纯健康样本作阴性类。

## 磨损模型

单个磨损标量 `w`（0=健康）同时驱动两件事：

1. **摩擦增大**：该关节 `viscous/coulomb/stribeck` 系数 ×(1+w)。
2. **振动/噪声**：注入扰动力矩 `d_tau = w·(宽带白噪声 + 随|qd|调制的轴承缺陷正弦)`，
   缺陷频率逐关节不同（37/43/53/61/71/83 Hz，均 <500Hz Nyquist）。幅值按关节力矩
   能力折算（满磨损约 1% 能力），属"轻度"。

磨损档位：`health` w=0；`light` w∈[0.15,0.35]；`moderate` w∈[0.5,0.9]。

## 文件格式

- `run_XXXX.npz`：每条一个。数组形状 `(N,)` 或 `(N,6)`，N=时间步，6=关节：
  - `t` 时间 [s]
  - `q` / `q_ref` 实际 / 参考关节位置 [rad]
  - `e` 位置误差 = q_ref−q [rad]
  - `qd` 关节速度 [rad/s]
  - `tau` 关节力矩 [N·m]
  - `vib` 关节角加速度 [rad/s²]——**振动通道**，含抖动 + 注入的轴承谱线
  - `p1` / `p2` 两腔压力 [Pa]
  - 标签：`w_vec`(6)、`worn_joint`(0=健康,1..6)、`level`、`seed`
- `manifest.csv`：每条样本一行（file/level/worn_joint/w/diverged + 概览特征）。

## 用哪些特征

**判别磨损用 `vib` 的高频分量（≥15 Hz），不要用原始 rms。** 原始 `vib`(=qdd)被
轨迹加速度(~0.25 Hz)主导，健康样本也很大；磨损信号是叠在上面的高频纹波，
必须先高通/带通或取 ≥15 Hz 频段能量。实测该特征逐关节单调可分（健康<轻<中）：

| 关节 | 健康 | 轻度 | 中度 |
|---|---:|---:|---:|
| J2 | 6.08 | 6.95 | 8.86 |
| J3 | 23.5 | 27.7 | 38.8 |
| J4 | 86.1 | 101.4 | 135.5 |
| J5 | 6.12 | 7.12 | 9.66 |

（J1 等重关节绝对量小、信号弱，仍单调。）提取示例：对每关节 `vib` 做 rFFT，
取 f≥15 Hz 的功率平方和开方；或在轴承缺陷频率(37/43/53/61/71/83 Hz)附近做带通。

- **次要信号**：`tau`（力矩 rms）——只有重关节(如 J1)随摩擦明显上升，不稳定，别单用。
- **弱信号**：`e`（位置误差）。PID 的积分项补掉了稳态摩擦误差，所以位置误差对
  磨损不敏感——这是**真实现象**（能补偿的控制器把误差藏起来了），正好说明为什么
  磨损监测要靠振动而非位置精度。

## 渐进磨损退化轨迹（预测性维护）

```
python wear_dataset.py --degradation --joint 4 --cycles 16 --w-max 0.9 --period 2.0
```

让磨损随运行周期缓慢增长（略加速 `w∝frac^1.4`），逐周期提特征，产出
`degradation_J{j}.csv` + `degradation_J{j}.png`（HF振动 / 力矩 / 真实磨损 三条趋势）。

实测 J4：HF振动 rms 随周期**单调上升** 91→152（+67%），力矩和位置误差全程平坦
（再次印证只有振动可用）。这条上升趋势正是预测性维护的输入——对它回归外推
"照此趋势多久到危险线"：

- 危险线取健康基线 1.5×（=137），只用**前 8 个周期**做线性拟合（斜率 3.1/周期），
  外推预计第 15.3 周期越线，**实际第 13 周期**越线，误差 ~2 周期。
- 趋势略上凸（磨损加速），线性外推略偏保守——真实且合理。

这与云端 `TrendService`（effort 分桶→最小二乘斜率→外推到异常基线上界）同一套路，
把振动派生指标喂给它即可做剩余寿命预估。

### 端到端实测（本地云栈，2026-09-23）

把 J4 退化数据按平台遥测格式（`joint_payload` 每关节 effort/velocity/position）
写入 device 4，分两窗喂给**真实运行的** `GET /api/analysis/devices/{id}/trend`：

| 喂进 effort 的特征 | TrendService 输出 | 结论 |
|---|---|---|
| 原始力矩 tau | 斜率 0.00/h，预计 2127h 到危险线 | 平稳，**检测不到磨损** |
| HF 振动 rms | 斜率 4.16/h，current 152→上界 175，**5.5h 触及危险线** | 正确捕捉退化 + 剩余寿命 |

结论：云端 `TrendService` 算法没问题，喂对特征就能出剩余寿命预警；缺口在**边端**
——要检测减速器/轴承轻度磨损，边端得算一个振动派生特征上报，云端现成分析直接可用。
（实测把振动指标暂借 effort 字段验证；正式接入应在遥测契约里加一个振动/健康特征字段。）

## 和平台主线的关系

生成的时序可直接喂给：边端 `edge/edge_node/fault` 故障检测、云端
`analysis` 的 `AnomalyService`（自适应基线越界）、`HealthService`（健康评分）、
`TrendService`（力矩趋势外推）。形成"孪生造数据 → 边端检测 → 云端分析"的闭环。
