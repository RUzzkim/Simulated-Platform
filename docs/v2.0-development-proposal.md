# 智控臂联 V2.0 研发方案（提案）

**版本**：0.1（方向已确认，实施参数待首轮复测冻结）  
**团队**：3 名成员  
**计划截止**：2026 年 12 月 9 日  
**验证范围**：工业机械臂仿真平台，使用 Python 仿真。实体机械臂、MATLAB 和 Gazebo 物理引擎均在本阶段验证范围之外。

## 1. 项目定位

V2.0 延续 V1.0 的端—边—云工业机械臂仿真平台，研究单关节卡滞后，系统能否判断原任务是否仍可完成，并据此选择任务恢复或安全停止。四个模块继续保留，围绕同一问题提供仿真工况、在线决策、实验记录与结果展示。

建议题目为《智控臂联 V2.0——面向单关节卡滞的工业机械臂容错控制与任务恢复仿真平台》。

## 2. 研究问题与目标

**研究问题**：单关节卡滞发生后，利用健康关节继续完成可达目标、对不可达目标安全停止，能否在控制故障关节负荷的同时提升任务处置效果？

**核心假设**：在统一仿真模型、轨迹和故障条件下，增加目标可达性判断及恢复/停止决策，相比 V1 容错策略可以改善可达任务恢复表现，并对不可达任务给出可验证的安全停止结果。该假设须由实验检验，不能预先作为成果结论。

目标包括复现 V1 基线，实现故障后的可达性判断、健康关节重规划和受控停止，以相同场景比较容错关闭、V1 和 V2 策略，并形成可演示闭环。

## 3. 范围边界

本阶段复用 V1 Python 仿真、ROS 2 接口、边缘算法、MQTT 链路和现有管理页面。首要故障为单关节卡滞，重点复测 LOCK-J1 失败工况并选其他关节作对照。场景包含可达和不可达目标。数值孪生使用 Python。

### 仿真入口与旧资产

- 成员 B 的离线卡滞实验使用通用六轴 DH 模型和 Python plant，可在仓库根目录直接复跑。演示回放现有实验轨迹时，末端位置和误差按该实验的 DH 参数解释。见[成员 B 实验说明](member-b-task-recovery.md)。
- 端边联调可暂用 `sim/gazebo_arm/` 中的轻量 Python 节点。Docker 默认入口运行 `sim_arm.launch.py`，以无头模式提供关节状态、关节指令和卡滞注入。见[容器启动入口](../sim/gazebo_arm/docker-entrypoint.sh)。
- `gazebo.launch.py`、物理场景、Gazebo 桥接及抓取脚本作为 V1 历史资产保留，退出 V2.0 部署、演示和验收流程。新版仿真端通过状态上报、指令接收和卡滞注入的端边联调后，再评估旧目录的迁移或归档。见[历史仿真入口](../sim/gazebo_arm/launch/gazebo.launch.py)。

真实机械臂、PLC、现场网络、多类故障、高精度外观重建、任意关节拖动、复杂抓取和全新商业级云平台不作为本阶段验收前提。

## 4. 系统架构与算法

```text
仿真端（ROS 2 / Python plant）
  任务轨迹、机械臂状态、卡滞注入
            │ joint_states / fault state
            ▼
边缘控制端（Python）
  状态处理 → 故障确认 → 可达性判断
  → 健康关节重规划 / 安全停止
            │ joint_command / telemetry / experiment events
            ▼
云端（现有 Spring Boot + MQTT + MySQL + Vue）
  实验索引、事件展示、曲线查询和回放
```

毫秒级控制留在仿真端与边缘端，云端只做记录、查询和展示。优先复用现有 ROS 2 与 MQTT 契约，字段变化向后兼容。

算法步骤为仿真端执行固定轨迹并注入位置卡滞，边缘端检测和确认故障，按健康关节约束判断目标可达性；可达时冻结故障关节并重规划健康关节，不可达或规划失败时有界减速停止。初版使用可解释、可复现的运动学约束搜索或逆运动学可行性检查。云端按 `run_id` 展示故障、决策、切换和结果。

## 5. 实验设计

| 组别 | 策略 | 用途 |
|---|---|---|
| A | 容错关闭 | 无故障处置基线 |
| B | V1 容错策略 | 现有故障降级基线 |
| C | V2 可达性判断及恢复/停止 | 新增策略评估 |

固定模型、起始姿态、轨迹、负载、控制周期和故障时刻。先复测 LOCK-J1，再覆盖其他关节和可达/不可达目标。每个场景用确定性种子重复运行，调参场景与验证场景分开，正式对照前冻结种子、划分和判据。场景数、重复次数和阈值在首轮复现后冻结，报告提供样本数和逐次数据。

可达目标指标包括恢复成功率、末端误差、恢复耗时、故障关节峰值力矩和切换耗时。不可达目标指标包括判定准确率、安全停止率、停止耗时及停止过程最大速度/力矩。系统指标包括控制周期耗时分布、遥测丢失率和运行稳定性，数值只能由实测记录得出。

**恢复成功**定义为末端进入预先冻结的目标容差并稳定保持，且不违反关节、力矩和速度边界。**安全停止成功**定义为在冻结时限内速度降至阈值以下且状态符合预设安全边界。**目标可达**定义为故障关节锁定后，至少存在一组满足关节约束和目标容差的健康关节解。相关阈值从 V1 参数和模型校核后预注册，不得依据结果回调。

每次运行记录 `run_id`、场景、种子、代码/模型/算法版本、目标轨迹、故障关节及注入/检测/确认时刻、可达性判定、决策/切换时刻、关节状态/命令/力矩序列、末端误差、结果和原因。原始数据与报告相互关联，大型数据不放入 Git。

## 6. 三人分工与协作接口

| 成员 | 主责 | 交付和接口 |
|---|---|---|
| A：仿真端与可视化 | 复用六关节模型、Python plant、场景和轨迹；配置卡滞并提供运行回放 | 向 B 提供状态、故障注入和命令接口；向 C 提供状态/事件 |
| B：控制与实验 | 复现基线，实现卡滞检测后的可达性判断、健康关节重规划、安全停止，运行对照实验 | 与 A 冻结状态/命令接口，与 C 冻结算法版本、事件字段和指标 |
| C：边缘/云集成 | 恢复 Docker/ROS 2/MQTT 链路，贯通实验编号、事件和存储，复用页面展示/导出 | 维护契约、运行配置、端到端测试并汇总团队材料 |

三人共同联调、冻结判据、复核结果、准备演示和申报材料。C 统筹格式，不独自承担全部技术内容撰写。

首周冻结统一字段：`run_id`；时间戳、关节名/位置/速度/力矩、末端位姿和场景 ID；故障类型/关节/注入和检测时刻；可达性、原因、策略和算法版本；任务状态、误差、峰值、耗时及判定原因。ROS 话题和 MQTT topic 优先沿用仓库契约，变更同步更新 schema 和测试夹具。

## 8. 验收标准

1. 新成员按文档可在 Docker 环境启动仿真与边缘闭环并复现一个基准卡滞场景。
2. 同一场景运行 A/B/C 三策略，每次都有 `run_id` 和原始记录。
3. 至少包含可达和不可达目标案例，给出冻结判据和结果。
4. 报告样本数、分布、失败案例及原始数据位置。
5. 演示故障、算法决策、恢复或停止及对应结果。
6. 所有性能结论标明仿真条件，不声称为工业现场实测。

## 9. 风险处理

- 在线联调或图形界面暂不可用时，先用 Python plant 完成算法验证，保留轨迹供回放。
- V1 结果不能复现时，记录依赖与差异，仅将可复现子集作为基线。
- 不可达任务的安全停止单独计分，不算作恢复成功。
- 重规划不稳定时收窄到单故障关节和固定工况，优先保证判定与停止正确。
- 端边云集成超期时先本地存储，之后再导入展示。
- 结果不足以支持提升时，报告适用范围和失败案例，不承诺未经数据支持的比例。
